# v1.1.0 — chantier en cours (non publiable)

Référence NemApi : commit `7441ce1` ; copie et adaptation autorisées par son propriétaire. Les pages adaptées sont servies uniquement dans `/next/` ; la page `/` de production est inchangée. Cette branche est expérimentale et ne doit pas être publiée comme release stable.

## Travail engagé et tests

- Import d’un seul provider à la fois, après confirmation de remplacement ; conservation des profils préexistants jusqu’à nouvel import.
- Interface de prévisualisation : tableau de bord, configuration, analytics, chat, clés web chiffrées au repos, intégrations. Le dashboard et le chat restent ouverts sur le réseau LAN choisi par l’utilisateur ; la protection des API est facultative. Une personne ayant accès à l’administration peut gérer et voir les clés web, et HTTP ne chiffre pas les échanges.
- Outils : formats `<tool>`, fences JSON d’outils connus, Qwen, invoke et certains DSML/DeepSeek. Huit tests instrumentés et un cycle `read_file` réel avec résultat simulé ont réussi ; il ne s’agit pas d’une parité complète des formats.
- SSE : premier événement immédiat, maintien périodique et sortie après copie complète. Un essai DeepSeek a duré 29,07 s, avec premier événement à 0,04 s, deux maintiens et 60 lignes ; un appel d’outil SSE a aussi réussi.
- Responses API partielle : JSON, SSE, outils de type function, historique explicite, image et alias DeepSeek testés en réel. `previous_response_id` est explicitement rejeté ; la compatibilité intégrale n’est pas implémentée.
- Intégrations expérimentales : profils Qwen Code, MonkeyCode et NEMESIS détectables et activables. Pour les deux premiers, le delta est envoyé uniquement si l’historique, les outils et un repère visuel correspondent. Un dialogue à deux tours et un cycle outil ont réussi en réel avec le profil Qwen. Un test NEMESIS a converti un appel natif en JSON produit par DeepSeek, sans liste OpenAI. Les trois commutateurs ont été testés dans un navigateur. Ces tests ne constituent pas des essais des logiciels agents complets.
- Après un changement manuel de conversation, réinitialiser explicitement le contexte : le repère d’accessibilité n’est pas un identifiant fiable de discussion. Une réponse identique dans deux conversations peut être ambiguë ; il n’y a pas de garantie d’isolation des conversations. Si le repère ne peut être lu, l’historique complet est renvoyé.
- Build debug et tests unitaires Gradle réussis ; derniers tests instrumentés ciblés (formats, historique, Responses et intégrations) : 22 réussis. Sous-requêtes locales et continuation sont disponibles de façon expérimentale et limitée, comme décrit ci-dessous ; cela ne constitue pas la parité avec NemApi.

Le profil DeepSeek doit être réimporté pour disposer des nouveaux sélecteurs. Les images temporaires sont visibles dans le sélecteur de documents système durant l’opération et stockées dans le cache privé jusqu’au nettoyage. Android 8.1 physique, autres sélecteurs système, JPEG et WebP ne sont pas encore validés.

- Basculer `/` uniquement après validation, puis construire et tester l’APK release signé. Après tous les critères satisfaits seulement : marquer v1.0.2 prérelease sans toucher ses assets et publier v1.1.0 stable.

## Concurrence et déconnexion (essais partiels)

- Génération longue réelle avec trois requêtes : premier événement SSE immédiat, troisième requête refusée `queue_full`, deuxième expirée `queue_timeout`, première terminée. La file d’attente est limitée avant tout accès à l’interface Android.
- Après fermeture anticipée du client SSE, la génération DeepSeek a continué : une nouvelle requête a été refusée `user_intervention_required` avant modification du champ. L’arrêt explicite a été demandé, puis une requête a réussi après stabilisation. La reprise immédiatement après l’arrêt a renvoyé 409 ; l’arrêt n’est pas synonyme de disponibilité immédiate. Ce seul essai ne valide pas toutes les formes de déconnexion ou les autres fournisseurs.

## Images (essais partiels)

- Avec DeepSeek 2.7.5 sur Android 13 émulé, image PNG rouge correctement reconnue via Chat Completions, Responses et chat web ; deux images rouge/bleu et huit images alternées reconnues dans l’ordre. Sélecteur système piloté par nœuds accessibles sans coordonnées enregistrées.
- L’historique contenant des images est retransmis dans son intégralité et les images sont de nouveau jointes avec des repères numérotés. Après création manuelle d’une nouvelle discussion DeepSeek, un deuxième tour a reconnu la couleur de l’image de l’ancien tour. Si l’historique ne tient pas dans la limite texte du provider, la requête est rejetée plutôt que tronquée ; l’envoi répété des images peut être coûteux.
- Les images sont mises en cache privé sous des noms aléatoires et exposées temporairement en lecture au sélecteur de documents Android. Elles sont retirées en fin d’opération, ou au prochain démarrage du fournisseur de documents après arrêt brutal. Ne pas considérer le cache ou les communications HTTP comme une protection contre les applications et personnes disposant d’un accès autorisé à l’appareil ou au réseau.
- L’import de provider ouvert avant démarrage du serveur est revérifié lors de la confirmation ; un test instrumenté a vérifié le refus en simulant un démarrage entre ouverture et confirmation.

## Sous-requêtes et continuation (expérimentales)

- Pour Qwen Code et MonkeyCode activés, les commutateurs `side_queries_local` et `continuation` sont configurables. Une suggestion ou une extraction mémoire reconnue peut recevoir une réponse locale neutre sans envoyer de texte dans la discussion ni changer sa session ; la sélection mémoire vide est limitée au schéma reconnu `selected_memories`. Un classifieur de sécurité est refusé : aucune décision n’est inventée. Les requêtes structurées générales et les outils ordinaires ne sont pas inventés localement. Un test HTTP avec DeepSeek hors premier plan a vérifié réponse locale, streaming, outil mémoire, refus de sécurité et absence de réponse locale pour des tâches normales.
- Une sortie d’outil JSON détectée comme tronquée peut déclencher jusqu’à quatre demandes de suite. Le recollement n’est accepté que pour un chevauchement exact d’au moins 24 caractères, unique dans le texte déjà reçu, et reste limité à 500 000 caractères. Si le recouvrement est absent ou ambigu, aucun appel incomplet n’est transmis. Premier essai réel : refus sûr pour suite ambiguë. Deuxième essai réel avec DeepSeek : un appel `write_file` volontairement tronqué a été complété et parsé ; ce seul cas ne valide pas les fichiers répétitifs, les longs outils ou tous les formats XML/DSML. Les essais synthétiques répétés sont refusés en cas d’ambiguïté. Les appels de continuation font l’objet d’un compteur, mais les estimations de tokens ne comptent pas précisément leurs prompts supplémentaires.
- Le parseur `<tool>` distingue les balises littérales à l’intérieur des chaînes JSON, rejette le texte parasite après un JSON et évite de produire un sous-ensemble valide lorsque d’autres appels sont invalides. Les parseurs Qwen/invoke/DSML rejettent certains résidus et doublons ; des détecteurs structurels repèrent certaines troncatures XML/DSML/V3. Les formats et leurs cas limites restent partiels ; ces garde-fous ne garantissent pas l’exécution complète.

## Correctifs de contexte et essais clients réels

- L’ancien plafond DeepSeek de 8 000 caractères pouvait supprimer silencieusement une instruction système de Qwen Code. L’historique des agents et celui avec images sont désormais refusés s’ils ne tiennent pas intégralement. Pour les autres clients, les anciens tours peuvent être supprimés mais les instructions système/developer sont conservées ou la requête est refusée. Le profil DeepSeek du chantier passe à 100 000 caractères ; il faut explicitement le réimporter. La limite globale d’un prompt, outils compris, reste 100 000 caractères : les conversations plus longues peuvent être rejetées même en mode incrémental. Le plafond n’est pas une garantie que chaque appareil ou fournisseur accepte un texte aussi long.
- Après le bouton Copier, le repère d’accessibilité doit maintenant différer du repère précédant la requête et rester stable sur quatre lectures avant d’être mémorisé. Deux cycles d’outil consécutifs et un dialogue réel ont ensuite utilisé le delta. Si le repère est absent, identique ou changeant, retour à l’historique complet ; cela ne résout pas l’absence d’identifiant fiable de discussion.
- NanoHTTPD 2.3.1 décodait `application/json` sans charset en US-ASCII : les caractères non ASCII étaient corrompus. Le serveur impose maintenant UTF-8 pour les corps JSON et refuse les autres charsets. Tests HTTP sur accents, chinois et emoji, avec et sans charset, puis réutilisation de la connexion après refus. Les tests se limitaient au build de prévisualisation et à Android 13 émulé ; la release v1.0.2 n’a pas été modifiée.
- Client réel Qwen Code 0.27.0, OpenAI-compatible sur USB/ADB vers DeepSeek 2.7.5 et Android 13 émulé : lecture d’un fichier de test par `read_file`, résultat transmis au modèle puis réponse exacte ; le texte système de 14 119 caractères, caractères UTF-8 compris, a été comparé exactement à celui visible dans DeepSeek. Un autre essai a exécuté `read_file` puis `edit` sur un fichier temporaire et validé ses octets. Un premier essai d’édition avait échoué : DeepSeek a remplacé le contenu sans inclure le saut de ligne existant dans `old_string`, créant une ligne vide supplémentaire tout en affirmant à tort avoir réussi. Le second, avec fichier initial sans saut de ligne, a réussi. Ces essais ne prouvent pas la fiabilité du modèle ni l’intégration de tous les clients.
- SDK Python officiel OpenAI 3.46.0 : Responses JSON, streaming texte, appel de fonction en streaming et propagation d’une erreur en streaming réussis en réel. Les événements Responses ont des numéros de séquence. `store=true`, `parallel_tool_calls=false`, formats JSON structurés et fonctions `strict=true` sont explicitement refusés plutôt que prétendus pris en charge. D’autres paramètres, dont `max_tokens`/`max_output_tokens`, température et certains réglages Responses, ne sont pas appliqués ni intégralement audités ; ils ne doivent pas être considérés comme des limites effectives. Les usages de tokens sont des estimations, pas une facturation réelle. Qwen Code envoie notamment `max_tokens`, qui n’est actuellement pas appliqué.

## Paramètres de génération non appliqués

Le client Android ne contrôle pas directement le modèle sous-jacent. Pour conserver la compatibilité avec les clients qui envoient des réglages par défaut, les champs identifiés mais non appliqués sont encore acceptés ; sur une réponse HTTP réussie Chat Completions ou Responses, `X-NemApi-Ignored-Parameters` énumère les champs non nuls reconnus comme ignorés. Cet en-tête est exposé aux navigateurs par CORS et est également émis avant le streaming. Notamment, `max_tokens`, `max_completion_tokens`, `max_output_tokens`, `temperature` et `top_p` **ne sont pas des garanties**. Des clients peuvent ignorer cet en-tête et la liste de champs n’est pas exhaustive ; ne pas utiliser ces paramètres comme garde-fous de sécurité ou de coût. L’audit des autres options et une politique plus stricte restent à faire.

Responses renvoie désormais `null` pour la température et `top_p` effectifs inconnus au lieu d’inventer la valeur 1. Tests Android : cinq tests instrumentés (audit et codec), build/unitaires réussis. Tests HTTP avec DeepSeek réel : en-tête Chat et en-tête Responses streaming corrects, températures et limites inconnues `null`. Régression SDK OpenAI Python : Responses JSON, streaming et outil en streaming réussis. L’en-tête ne signifie pas que ces paramètres fonctionnent.

Des garde-fous refusent désormais `n > 1`, les séquences `stop` non vides et les probabilités de tokens demandées ; les types invalides correspondants sont refusés. Ils ne mettent pas ces fonctions en œuvre. Vérifications : six tests Android ciblés, six refus HTTP de contrat et quatre champs invalides, avertissements HTTP JSON/streaming avec DeepSeek et nouvelle lecture par le CLI NEMESIS réel. La page de configuration `/next/config` affiche la compatibilité partielle et l’avertissement sur les limites non appliquées. Après instrumentation, une erreur système de l’émulateur a nécessité son redémarrage et la relance de System UI ; un premier essai de régression a échoué avec `wrong_app` durant cet incident, puis a réussi après rétablissement.
