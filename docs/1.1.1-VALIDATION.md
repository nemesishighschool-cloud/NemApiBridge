# Journal de validation — 1.1.1 (candidat)

## Portée

Les essais ci-dessous utilisent un émulateur Android 13 avec DeepSeek 2.7.5 en anglais. Ils ne prouvent ni le fonctionnement sur un téléphone physique, ni la compatibilité de tous les claviers, versions de DeepSeek, versions Android, sélecteurs de fichiers ou réseaux Wi-Fi. Le serveur HTTP et l’interface web sont conçus pour un réseau privé de confiance.

## Mesures et régressions

- Avant optimisation, sur quatre réponses, la première observation exploitable de réponse inactive précédait le début de copie d’environ 2,28–2,30 s (profil à 750 ms, trois vérifications). Après, sur quatre réponses comparables, l’écart observé était d’environ 0,948–0,956 s (profil à 300 ms, trois vérifications). La mesure après porte sur un build debug du code final, avec le garde-fou remettant les vérifications à zéro pendant la génération ; le binaire signé n’a pas fait l’objet de la même instrumentation temporelle. L’instant exact de fin de génération peut précéder la première observation ; ces mesures ne sont pas une mesure universelle de bout en bout. La vérification du presse-papiers et sa copie prennent encore du temps et dépendent de l’appareil.
- Avant correction, une réponse de 20 lignes complètes s’est bloquée : une phase de défilement avait masqué l’observation de la génération. Le suivi a été déplacé dans la boucle de défilement, avec retour au contrôle pendant la génération. Après correction, six essais de 20 lignes ont restitué les 20 lignes exactes dans l’ordre ; quatre séries comprenaient également chacune trois réponses courtes, dont une réponse identique répétée. Cela réduit le risque observé sans prouver l’absence de tous blocages ou anciennes réponses.
- Test navigateur via une adresse privée et relais ADB vers l’émulateur : image choisie côté navigateur, réponse réelle DeepSeek sur la couleur, puis question de suivi. Pas de fichier image préalablement placé sur le stockage partagé Android. Ce relais ne remplace pas un essai Wi-Fi physique.
- Test ciblé du sélecteur d’applications Android : choix de l’application DocumentsUI système dans un écran réel à plusieurs options. Test complet séparé avec application cible de test : navigateur → choix Android forcé → DocumentsUI en grille → passage en liste → image reçue et ouverte par l’application de test → réponse. Le parcours forcé a également réussi avec l’APK signé final ; les fichiers temporaires ont été retirés du cache après la requête. L’application cible de test n’est pas DeepSeek ; le test réel DeepSeek ci-dessus ouvrait directement DocumentsUI sans choix intermédiaire.
- Les tests unitaires couvrent notamment le rejet d’un libellé de sélecteur ambigu ou partagé avec une autre application. Les autres variantes OEM et langues restent non validées ; en cas d’ambiguïté ou d’écran non reconnu, l’automatisation échoue et demande une intervention.

## Reproduction ciblée du choix d’application

Sur un émulateur de test uniquement, préparer les deux APK de tests avec JDK 17 et le SDK installé : `tests/resolver-probe.sh` puis `tests/full-chooser-fixture.sh`. Installer les APK indiqués par ces scripts. Le test d’instrumentation `SystemResolverIntegrationTest` exige `test.resolver` ; il modifie temporairement les réglages d’accessibilité et peut arrêter ou réinstaller l’application testée. Le scénario web `tests/full-chooser-web.cjs` exige Playwright, les deux APK de test, un provider de test pointant vers `test.fullchooser` et le serveur en marche. `NEM_URL` permet de choisir l’adresse de test. Ne jamais lancer ces manipulations sur les données d’un utilisateur réel.

## Réserves

- L’arrêt de la requête n’est pas une garantie d’arrêt de la génération cible.
- La sélection automatique ne reconnaît que les composants système prévus et ne choisit pas de défaut permanent ; les variantes inconnues demandent une intervention.
- La vitesse et la fidélité du bouton Copier dépendent de DeepSeek. En l’absence de preuve de réponse nouvelle ou complète, l’automatisation doit échouer plutôt que retourner une ancienne réponse.
- Le keystore de signature publié volontairement est compromis ; aucune confiance dans l’identité du signataire ne doit lui être attribuée.
